# `1.0.0` → `1.1.0` migration

**Status:** **Planned — not shipped.** `v1.1.0` has never been tagged.
(This document previously read "Status: GA", which was incorrect.)
**Last refreshed:** 2026-08-04 (versions, paths, and every export claim
re-verified against the tree).
**Target audience:** host apps upgrading from `@anvilkit/*@^1.0.0`
to `@anvilkit/*@^1.1.0`.

> **Version reality check.** No `1.x` release exists. The runtime cone ships
> **`0.1.18`** today and `packages/runtime/core/CHANGELOG.md` contains no
> `1.x` entry, so neither the `1.0.0` this migrates *from* nor the `1.1.0` it
> migrates *to* was ever cut.
>
> **The features below are real.** Every surface described in § 2 was
> verified present in the current tree — `@anvilkit/schema/section`,
> `@anvilkit/validator/section`, `@anvilkit/ir/migrations`,
> `@anvilkit/ui/presence`, `PageIRNodeMeta`, and the `anvilkit add`
> command all exist and are shipping on the `0.1.x` line. Only the version
> labels are fiction: read "new in 1.1" as "available today in `0.1.x`",
> and ignore the `^1.1.0` ranges until the cut actually happens.

`v1.1.0` is **purely additive** over `v1.0.0`. No public type
narrows, no export is removed, no covered semantic shifts. The
[`docs/policies/lts.md`](../policies/lts.md) commitment from
`1.0.0` carries forward unchanged for every covered surface; the
new `1.1.x` clock starts on `v1.1.0` ship and runs in parallel
with the remaining `1.0.x` patch window per
[`docs/policies/lts.md`](../policies/lts.md) § 1.

**No code changes are required to upgrade.** Bumping the version
range from `^1.0.0` to `^1.1.0` in your `package.json` is enough.
The new surfaces below are opt-in; ignoring them is a supported
path.

Realtime collaboration ships separately and is **not** under the LTS

[`docs/policies/lts.md`](../policies/lts.md) § 7.1):

```sh

```

The plugin has moved well past the `0.1.0-alpha.x` line this section was
written against — it is on **`0.10.0-rc.10`** today, a release-candidate
rather than an alpha, and it now also carries `@hocuspocus/provider` and
`y-websocket@^3` as peer dependencies. Pin exact versions; the pre-1.0
line still breaks between releases.

The two CLIs are published outside the fixed group and are planned to
reach `1.1.0` at the same time on the `latest` dist-tag. Their real

## 2. What's new (additive)

### 2.1 Section-level AI editing — `phase6-001` … `phase6-005`

A new selection-aware AI flow lets authors regenerate an arbitrary
node subtree without losing surrounding canvas state. Two new
subpath exports power it:

- **`@anvilkit/schema/section`** — exports `AiSectionContext` (the
  schema slice describing the surrounding zone and the allow-list of
  replacement node types) and `configToAiSectionContext(config,
  selection)` to derive that context from a Puck `Config` plus a
  selection. Pure-function, no React import.
- **`@anvilkit/validator/section`** — exports
  `validateAiSectionPatch(patch, ctx)` enforcing patch shape, node
  validity, prop serializability, and zone allow-list membership.
  Returns a structured `ValidationResult` with stable codes:
  `PATCH_SHAPE`, `INVALID_NODE`, `NON_SERIALIZABLE_PROP`,
  `DISALLOWED_COMPONENT`.

`@anvilkit/plugin-ai-copilot` now accepts an optional
`generateSection` callback alongside the existing `generatePage`
flow. When set, the plugin exposes a `regenerateSelection(prompt,
selection)` action that:

1. Reads current canvas via `puckApi.getAppState().data`.
2. Builds an `AiSectionContext` via `configToAiSectionContext`.
3. Invokes the host-supplied `generateSection(ctx, prompt)`.
4. Validates the result via `validateAiSectionPatch`.
5. On success, dispatches
   `puckApi.dispatch({ type: "setData", data: applyPatch(currentData, patch) })`
   so surrounding selection / scroll / sidebar state is preserved.
6. On failure, surfaces the structured `ValidationResult` to the
   prompt panel.

The existing `generatePage` flow is untouched — `regenerateSelection`
is purely additive and gated on `generateSection` being provided.

The Studio prompt panel auto-switches modes based on Puck selection
state (zero selection → "Generate page", 1+ selection →
"Regenerate selection"). No host-side wiring is required if you use
the default panel.

### 2.2 Authoring metadata on `PageIRNode` — `phase6-006` … `phase6-009`

`PageIRNode` gains an optional `meta` field for collaborative
authoring metadata:

```ts
export type PageIRNodeMeta = {
  locked?: boolean;        // editor blocks edits when true
  owner?: string;          // host-owned identifier (≤ 256 chars)
  version?: string;        // semver-shaped string
  notes?: string;          // freeform author notes (≤ 512 chars)
};

export type PageIRNode = {
  // …existing fields unchanged…
  meta?: PageIRNodeMeta;   // optional — back-compat with 1.0
};
```

`puckDataToIR()` **never** synthesises `meta` — it remains an
authoring-time concept owned by the host or by
`plugin-version-history`. Round-tripping a `1.0`-era IR through any
`1.1` exporter or validator is a no-op.

A new subpath, **`@anvilkit/ir/migrations`**, exports the upgrade
helpers:

- `migratePageIR(ir, { from: "0.21", to: "0.22" })` — no-op when
  `meta` is absent; opt-in `meta: {}` initialisation when called
  with `withMeta: true`.
- `downgradePageIR(ir)` — strips `meta` for `1.0`-only consumers.
- `MIGRATION_VERSIONS` / `PageIRMigrationVersion` /
  `PageIRMigrationOptions` types.
- `PageIRNodeMetaError` / `NodeMetaValidationIssue` for typed
  failure reporting.

`@anvilkit/plugin-version-history` surfaces `meta` field deltas as
a new `metaChanged` diff category. The version-history sidebar
renders meta diffs and the canvas overlays a presence-style mark
on locked nodes.

Field-level Zod caps:

| Field           | Constraint                       |
| --------------- | -------------------------------- |
| `meta.notes`    | ≤ 512 chars                      |
| `meta.owner`    | ≤ 256 chars                      |
| `meta.version`  | Semver-shaped regex              |
| `meta.locked`   | Boolean                          |

LTS commitment: removing `meta` is forbidden until `v2.0.0`;
renaming a sub-field requires a major bump. Adding new sub-keys to
`PageIRNodeMeta` requires architecture review.

### 2.3 Marketplace + `anvilkit add` — `phase6-010` … `phase6-014`

The CLI gains an `add` subcommand that resolves against a curated
registry feed and codemods host-side configs:

```sh
npx anvilkit add @anvilkit/template-landing-saas
```

Resolution order:

1. Registry-feed allow-list lookup (cached locally for 24 h from
   `https://docs.anvilkit.dev/registry/feed.json`).
2. On `--unsafe`, raw npm resolution with a red warning.

By default the command runs in **`--dry-run`** mode and prints the
diff. Pass `--write` to apply codemods. Mutated files, resolved in
**your** app (the CLI walks a candidate list rather than a fixed path —
see `packages/tooling/cli/src/commands/add.ts`):

- The Puck config — first match of `lib/puck-config.{ts,tsx}`,
  `src/lib/puck-config.ts`, `app/puck-config.ts`, or
  `puck-config.{ts,tsx,js}` — gets the import + the `Config.components`
  entry.
- `next.config.{js,ts}` — the `transpilePackages` entry.

(In this repo the equivalent wiring lives at
`apps/studio/lib/puck-demo.ts` and `apps/studio/next.config.js`; there
is no `apps/web`.)

Codemods are idempotent (`recast` + `@babel/parser`) — running
twice is a no-op on the second run.

New first-party docs:

- [`docs/policies/marketplace-feed.md`](../policies/marketplace-feed.md) —
  registry feed JSON schema (versioned, signed-checksum,
  `kind: plugin|template|component`, `verified` flag, scorecard).
- [`docs/policies/marketplace-governance.md`](../policies/marketplace-governance.md) —
  submission, review, verification, and rejection policy. Linked
  from the root [`CONTRIBUTING.md`](../../CONTRIBUTING.md) §
  "Marketplace Submission".
- `apps/docs/src/routes/marketplace.tsx` — filterable catalog rendering
  at `https://docs.anvilkit.dev/marketplace`, with the presentational
  component in `apps/docs/src/components/marketplace-catalog.tsx`. (This
  was an Astro page when the section was drafted; the docs app has since
  moved to Fumadocs on TanStack Start, so no `.astro` file remains.)
- `.github/workflows/marketplace-scorecard.yml` — automated
  scorecard CI gating registry-feed PRs.

### 2.4 `SnapshotAdapter` v2 — `phase6-015`

`@anvilkit/plugin-version-history` extends the Phase 5
`SnapshotAdapter` interface with two **optional** members:

```ts
export type SnapshotAdapterV2 = SnapshotAdapter & {
  subscribe?(onUpdate: (ir: PageIR, peer?: PeerInfo) => void): Unsubscribe;
  presence?: {
    update(state: PresenceState): void;
    onPeerChange(callback: (peers: PresenceState[]) => void): Unsubscribe;
  };
};
```

The base `save / list / load` methods are unchanged. Existing
`inMemoryAdapter` and `localStorageAdapter` continue to compile —
no host-side change is required unless you opt into v2 features.

### 2.5 Presence UI primitives — `phase6-017`

New subpath **`@anvilkit/ui/presence`** ships:

- `<PresenceCursor>` + `PresenceCursorProps`
- `<PresenceLayer>` + `PresenceLayerProps`
- `<PresenceSelectionRing>` + `PresenceSelectionRingProps`,
  `PresenceSelectionRingRect`
- `usePresence()` hook + `PresenceCursorCoords`, `PresencePeer`,
  `PresenceSelectionState`, `PresenceSource`, `PresenceStateFrame`,
  `UsePresenceOptions`, `UsePresenceResult` types.

Subpath only — the `@anvilkit/ui` root entry's bundle size is
unchanged.

## 3. Behavioural fixes (non-breaking)

The two `validateAiOutput` / `validateComponentConfig` defects
closed in `1.0.0` (F-2, F-3 — see
[`docs/policies/lts.md`](../policies/lts.md) § 4) remain in force.
`v1.1.0` does not introduce any further behavioural shifts on
covered surfaces. If a host hits a behavioural change not listed
here, it is a regression — please file an issue.

## 4. Breaking changes

**None.** The `1.0.0` LTS contract holds for every covered surface.
Anything that would force a breaking bump (cross-framework
exporters, plugin sandboxing GA, asset CDN) defers to `v2.0.0`.

## 5. Realtime alpha channel

`@anvilkit/plugin-collab-yjs` is explicitly **outside the LTS
commitment**. It has advanced from the `0.1.0-alpha.x` line this section
was drafted against to **`0.10.0-rc.10`**, but the limitations below
still hold — the plugin continues to use the whole-document JSON blob
encoding, so the "alpha-only edge cases" remain current. See:

- [`docs/policies/lts.md`](../policies/lts.md) § 7.1 —
  alpha-channel rules.
- `docs/archive/announcements/2027-12-v1-1-ga.md`
  § "Alpha caveats" — the limitations list (no per-prop merge, advisory
  `meta.locked`, ephemeral awareness, no backpressure, no conflict
  diagnostics). This announcement was drafted for a release that never
  shipped and is now archived.
- [`docs/architecture/realtime-collab.md`](../architecture/realtime-collab.md)
  § 6 — the canonical, still-maintained "known alpha-only edge cases"
  reference. Prefer this one.

Hosts adopting the plugin should pin exact versions and expect breaking
changes between pre-1.0 releases. Graduation to per-prop merge is still
pending.

## 6. Deprecations

No exports are deprecated in `1.1.0`. The deprecation policy from
[`docs/policies/lts.md`](../policies/lts.md) § 5 remains in force —
any `@deprecated` marker added in a `1.x` minor must remain
callable for at least two subsequent minors (~6 months) before
removal.

## 8. Exit-cut runbook

For the release lead only. Consumers do not run any of these steps.
The standalone `docs/release/release-runbook.md` was never written; the
executable source of truth is `.github/workflows/publish.yml`.

1. Land all queued M13 changesets. `pnpm changeset status
   --verbose` confirms only expected bumps go out (every fixed-group
   package → `1.1.0`; `plugin-collab-yjs` → `0.1.0-alpha.N+1`).
2. Trigger the `Publish` workflow with the standard `latest` mode
   via `workflow_dispatch`. The fixed group publishes to `latest`.
   `plugin-collab-yjs` publishes to `alpha` — verify with `npm view
   @anvilkit/plugin-collab-yjs dist-tags` after the run.
3. Merge the auto-opened "Version packages" PR.
4. Tag the release: `git tag v1.1.0 && git push --tags`.
5. Land the docs banner flip in `apps/docs/content/docs/index.mdx`
   (the Fumadocs content root — the old `apps/docs/src/content/`
   Astro layout is gone) and finalise the header stamp on the
   announcement, now archived at
   `docs/archive/announcements/2027-12-v1-1-ga.md`.
6. Vercel redeploys the docs site automatically on merge to
   `main`; confirm the `1.1` banner is live at
   `https://docs.anvilkit.dev`.

Steps 1–4 are automated by the existing `phase5-019 phase4-017`
release machinery; steps 5 and 6 are the only manual M13 hand-offs.
